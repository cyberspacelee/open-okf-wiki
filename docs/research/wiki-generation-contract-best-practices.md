# Repo Wiki 信息架构与质量门禁最佳实践

日期：2026-09-01  
访问日期：2026-09-01  
范围：greenfield contract，不考虑旧 Run、Artifact 或 schema 的兼容与迁移。
资料只采用官方规范、官方项目文档和官方源码。

> 证据边界：外部资料给出 topic 粒度、typed content、导航、显式依赖、
> provenance、schema 和图语法的通用机制；它们不规定 repo-wiki 的字段名、
> 路径前缀或 review 阶段。本文把“资料直接支持的事实”和“对 repo-wiki 的设计推论”
> 分开陈述。能力域路径、merge probe 记录格式和 evidence 文件布局是本项目策略，
> 不是外部规范原文。

## 结论

这组问题不能靠补写缺失的五页或放宽 validator 解决。完整修复应同时建立五个闭包：

1. **粒度闭包**：Plan 和 Composition 都必须记录双向的 split/merge probe；不设 merge
   数量配额，但禁止只检查 split。
2. **导航闭包**：Composition path 表达能力层级；根目录和每个非叶目录都有确定性
   `index.md`；所有页面从根 index 可达。
3. **证据闭包**：cross-source unit 在 Plan 中显式声明 producer、consumer 及必要的
   contract/feedback 证据；页面使用的每个 locator 都落在继承 scope 内。
4. **表达闭包**：页面类型和能力子型共同选择模板；规则、编排和计算使用不同的必需
   结构，不能再共享固定四节。
5. **引用闭包**：YAML parse、typed schema、跨字段 join、locator、Mermaid syntax 和
   diagram evidence 分层验证；任何一层失败都阻断后续阶段。

推荐 lifecycle：

```text
source-qualified evidence
  -> Plan: unit boundaries + participant-complete scopes
  -> Plan review: split probe + nearest-neighbor merge probe
  -> Composition: page grouping + capability paths + template profile
  -> Composition review: split/merge/move + navigation reachability
  -> Write: typed frontmatter + claim/diagram evidence
  -> deterministic validation
  -> generated root/section indexes
  -> semantic review + publish
```

## 1. 双向粒度审查：解除只拆不并的单向棘轮

### 一手资料

[OASIS DITA 1.3：topic 是基本信息单元](https://docs.oasis-open.org/dita/dita/v1.3/os/part3-all-inclusive/archSpec/base/topicdefined.html)
将 topic 定义为：足够短，聚焦单一 subject 或 reader question；又足够长，能独立理解并作为
一个自包含单元创作。这个定义同时给出了拆分的上界和合并的下界。

[OASIS DITA 1.3：chunking](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/base/chunking.html)
明确允许在交付时 split 一个多 topic 文档，也允许 combine 多个 topic 为一个输出文档。
因此成熟的 topic 模型不是“越拆越正确”，而是同时支持 divide 和 merge。

[OASIS DITA 1.3：DITA map elements](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/ditamap-elements.html)
允许用 `collection-type` 表达 choice、sequence 和 family 等关系。相邻内容是否应合并，
取决于它们共同回答的问题和关系，而不是源文件数或 unit 数。

### 对 repo-wiki 的设计推论

Plan review 和 Composition review 都应执行同一套双向 routing sweep：

| Probe | 必答问题 | 失败后的操作 |
|---|---|---|
| Split | 该 unit/page 是否包含两个可分别提出、分别变更或分别排障的问题？ | `split` |
| Standalone | 拿掉 sibling 后，它是否仍能回答一个可路由问题并独立成立？ | 否则进入 merge probe |
| Merge | 哪个相邻 unit/page 与它共享 reader entry point、evidence neighborhood 和 maintenance session？分开是否迫使读者重建同一因果链？ | `merge` 或记录 `keep-separate` 理由 |
| Move | 内容成立，但能力父级或路径是否让读者从错误入口进入？ | `move` |

不要设置“至少产生一个 merge”的配额。正确的硬约束是**每个 unit 都有 split 记录，且至少被
一个 nearest-neighbor merge probe 覆盖**；没有候选时必须记录原因。review report 应使用
typed records 表达 `split | merge | keep | move`，kernel 验证 probe coverage，reviewer 判断语义。

候选邻居不需要做全量 O(n²) 比较。先按以下任一关系形成小簇，再在簇内选择 nearest neighbor：

- 共享 Source 且 scope 相同、相交或存在祖先关系；
- 属于同一显式 handoff、sequence 或 family；
- Composition 提议位于同一能力目录；
- 共享同一读者入口和维护会话。

必须写入 contract 的反例：

- 同一个 evidence note 不构成拆页理由；
- 同一个 service/package 不构成合页理由；
- 页短不自动合并，页长不自动拆分；
- 顺序相邻但独立变更的阶段保留为独立页，用 bridge page 或链接表达 handoff；
- 两页都不能脱离对方自洽时，不得以 unit 边界为由保持一页一 unit。

这会直接阻断“22 unit -> 22 page”的机械映射，同时保留真正独立的覆盖义务。

## 2. 能力路径、渐进式 index 与导航闭包

### 一手资料

[OASIS DITA maps](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/ditamap-elements.html)
用嵌套 topic references 定义 TOC、在线导航、父子链接和非层级关系；导航是显式的信息架构，
不是文件名列表的副作用。

[MkDocs：Writing your docs](https://www.mkdocs.org/user-guide/writing-your-docs/)
说明文件布局会形成 URL，支持嵌套目录，并把目录中的 `index.md` 或 `README.md` 作为 section
index。它给出了“物理层级 + 局部入口页”的直接实现先例。

[Docusaurus：Autogenerated sidebars](https://docusaurus.io/docs/sidebar/autogenerated)
从目录生成 category、从文件生成 doc link，并支持每个目录的 category index。官方文档还明确
识别 `index.md`、`README.md` 或同目录名文件作为 category index。

[Sphinx：toctree directive](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html#directive-toctree)
把文档是否进入导航树当作可检查状态；未进入标准导航的文档会产生 warning。这是“页面存在”
与“页面可达”必须分别验证的成熟先例。

### 对 repo-wiki 的设计推论

本项目已经决定 physical path 同时承担最终 hierarchy 和 navigation binding，因此应把
capability-oriented path 从写作建议升级为硬门禁。多页 Wiki 的默认形状应是：

```text
index.md
accounting/
  index.md
  object-lifecycle.md
  document-pipeline.md
  equity-method/
    index.md
    measurements.md
contract/
  index.md
  fulfillment.md
integration/
  index.md
  collection-accounting.md
```

具体目录名由 Source 中的能力和读者任务决定；上例只说明层级，不是领域事实。顶层优先表达
`accounting`、`contract`、`integration`、`operations` 等能力簇，不使用 `flow/`、`domain/`
这类页面类型目录。cross-source handoff 放在 reader-facing 的 integration/capability 路径中，
而不是复制进两个 Source 目录。

Composition path gate 至少验证：

- POSIX normalized、bundle-relative、Windows portable、唯一；
- 多页 bundle 的普通页面至少有一个 capability directory segment；
- 同能力子簇存在多个独立页面时使用二级目录，避免所有内容平铺；
- 目录名和 page slug 是稳定语义词，不使用完整 hash 作为人类可见名称；
- `index.md` 和 `log.md` 由 kernel 保留，不能成为普通 page path；
- draft 在 Composition 已绑定 path 后写到 `work/drafts/<composition.path>`，不再按 page ID
  裸平铺；稳定 page ID 仍用于依赖、review 和状态，不需要等于 path。

Index 不应由 writer 手写。kernel 从 approved Composition 确定性生成：

- 根 `index.md`：能力目录、直接页面、短 routing description；
- 每个非叶目录的 `index.md`：child directories、direct pages、各自 description；
- 稳定排序和 bundle-relative link；
- 生成过程中可刷新 draft preview index，Publication 再从最终 Candidate 重建。

最终 navigation closure：

```text
composed page paths
  == published non-reserved Markdown paths
  == leaves reachable from root index
```

同时拒绝 orphan page、dangling child、循环目录链接、重复入口和指向未发布 draft 的链接。
进度数字也应从 Plan/Composition 状态派生；不要让 `progress.md` 手写“15 units”之类会漂移的计数。

### 当前实现说明

当前 `_publish.render_indexes()` 已经生成根与嵌套 `index.md`，bundle validator 也检查 index
frontmatter 和链接。因此某个卡在 write 阶段的 Run 没有最终 index，不等于 Publication 缺少 index。
需要补的是 Composition 后的分层 path、draft preview 导航，以及一条证明所有最终 page 可达的集合等式。

## 3. Cross-source scope 与 evidence closure

### 一手资料

[Bazel remote caching](https://bazel.build/remote/caching)
把每个 action 建模为显式 inputs、output names、command line 和 environment；required inputs 与
expected outputs 都由 action 声明。遗漏输入会破坏可复现性和 cache correctness。

[Bazel hermeticity](https://bazel.build/concepts/hermeticity)
要求产物只依赖已知、固定身份的输入。这与 Wiki page 只能使用 declared scope 内 frozen Source
证据具有相同的闭包结构。

[W3C PROV-O](https://www.w3.org/TR/prov-o/)
用 `used`、`wasGeneratedBy` 和 `wasDerivedFrom` 建立 activity 与 entity 的 provenance chain；
官方示例直接用 dataset -> activity -> chart 表达产物来源。

[W3C PROV Constraints](https://www.w3.org/TR/prov-constraints/)
定义 provenance 实例的一致性约束，说明“记录了一些来源”不等于 provenance 自洽，关系仍需
独立验证。

### 对 repo-wiki 的设计推论

Page 是由 frozen evidence 生成的 artifact。它应像 hermetic action 一样，在执行前拥有完整输入声明：

```text
locators used by claims and diagrams
  subset of page inherited scopes
  subset of frozen registered Sources
```

cross-source unit 不能只用自由文本暗示 handoff。建议把每个 scope record 改成 participant-complete
结构，使 seed 与 Source 不再分离：

```yaml
scopes:
  - source: Contract
    role: producer
    paths: [contract/.../deemed]
    evidence_seeds:
      - Contract/contract/.../MqsProducer.java#L40-L72
  - source: Accounting
    role: consumer
    paths: [accounting/.../deemed]
    evidence_seeds:
      - Accounting/accounting/.../MqsConsumer.java#L30-L81
```

`role` 至少允许 `owner | producer | contract | consumer | feedback`。完整 gate：

- `integration` unit 至少有两个不同 Source；
- cross-source causal unit 至少有 `producer` 和 `consumer`；
- 每个 participant 至少有一个实际打开过、位于其 paths 内的 seed；
- protocol/enum/topic 在独立位置时增加 `contract` participant；
- 有 callback、retry result 或状态回写时增加 `feedback` participant，或记录证据化 gap；
- participant 的 Source/paths/seeds 在 Plan review 前全部 resolve 到 frozen revision；
- Composition 合并 unit 时取 participant scope 的 union，不丢任何一侧；
- Page 必须引用每个参与 Source，diagram 还必须覆盖其实际展示的 participant。

任何一项缺失都应在 Plan gate 失败，不允许 writer 用 `coverage: partial` 掩盖 planner-controlled
的 scope 漏声明。`partial` 只表达 frozen Source 确实缺证据、依赖未注册或有界调查无法确认的真实 gap。

### Evidence note 分区

巨型 `remaining-domains.md` 确实妨碍路由。默认采用：

```text
work/evidence/<source>/<bounded-question>.md
```

一份 note 默认调查一个 Source 中的一个问题；cross-source synthesis 留在 Plan，由多个 note 提供输入。
但不要把“一个文件只能含一个 Source”误当作正确性机制。真正的 invariant 是**每条 evidence 都有
Source-qualified locator，且使用它的 unit scope 覆盖该 locator**。问题导向的 cross-source note 在
每条记录都带 Source 身份时仍然可以合法存在；文件夹分区只改善可发现性，不能替代依赖闭包。

## 4. 按能力子型选择模板与表达

### 一手资料

[OASIS DITA 1.3：DITA topics](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/base/topicover.html)
明确区分 concept、task 和 reference 等 information types，并说明不同读者问题应使用不同类型。

[OASIS DITA 1.3：Concept topic](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/technicalContent/dita-concept-topic.html)
用于解释 process、function 或其他主要 abstraction，帮助读者建立理解。

[OASIS DITA 1.3：General task topic](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/technicalContent/dita-generic-task-topic.html)
围绕 reader goal 组织 context、ordered/unordered steps、result、troubleshooting 和 next action。

[OASIS DITA 1.3：Reference topic](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/technicalContent/dita-reference-topic.html)
用于可查阅的事实、参数和规范，正文原生偏向 table、property list、syntax 和 example。

这些规范共同说明：统一标题骨架不等于一致性；一致性来自先识别 information type，再约束适合该类型
的内容结构。

### 对 repo-wiki 的设计推论

先修正顶层 page-type routing：

- “系统由谁组成、边界如何连接” -> `Architecture`；
- “按什么顺序跨参与者执行、失败后怎样恢复” -> `Flow`；
- “对象有哪些状态、转换和非法边” -> `Lifecycle`；
- “实体/字段/关系/ownership 是什么” -> `DataModel`；
- “能力受哪些规则、计算和共享语义约束” -> `Domain`。

然后只对 `Domain` 增加最小必要的 `profile`，不要复制出更多顶层 page types：

| Domain profile | 必需内容 | 不应强塞的内容 |
|---|---|---|
| `constraint` | 职责边界；紧凑规则表；状态/约束 owner；可观察失败 | 没有实际顺序时的伪流程 |
| `orchestration` | trigger/input；ordered stages/branches；state effects；failure/compensation；handoff | 为填模板重复共享锁和通用幂等规则 |
| `calculation` | 输入/输出；grouping/order；公式；符号、精度和舍入；异常边界 | 字段 inventory 或无证据示例 |

规则表固定为：

| Rule / invariant | Condition | Enforcement location | Observable failure/effect | Evidence |
|---|---|---|---|---|

这样 `coverage` validator 可以检查真实结构，而不是只检查四个标题存在。编排/算法页还应允许：

- Mermaid sequence/flowchart 表达参与者和分支；
- 公式 code/math block 表达 PPA、grouping、取反和 rounding；
- 紧邻公式的输入、输出、边界条件和 locator；
- 正常路径之外的 retry、rollback、compensation 和 terminal failure。

字段清单只进入 `DataModel` 或 `Table/reference` page。Flow 的 trigger/result 只描述业务触发、状态变化、
外部效果和失败，不复制 entity 字段。

重复的 Redis lock、幂等计数、状态优先级或 after-commit 语义只在一个 canonical capability page 定义；
其他页用 logical link 引用。只有当这些 shared contracts 本身通过 Task Routing Test 时才创建独立页；否则
把它们放在共同 owner page，不为“去重”制造空壳页面。

模板 gate 应根据 `type + profile` 选择 required、allowed 和 forbidden sections，并拒绝空占位。不要让
writer 自由选择 profile；Composition 绑定，Candidate 必须原样继承。

## 5. Frontmatter、citation 与 diagram 的分层验证

### 一手资料

[YAML 1.2.2](https://yaml.org/spec/1.2.2/)
定义 mapping、sequence 和 scalar 三种节点；`>` 是 folded block scalar，换行折叠后仍是一个 scalar
字符串。由此可知，YAML 解析成功不能证明 `coverage` 的值具有正确业务语义。

[JSON Schema：enum](https://json-schema.org/understanding-json-schema/reference/enum)
用 `enum` 把值限制在固定集合；[object](https://json-schema.org/understanding-json-schema/reference/object)
支持 `properties`、`required` 和禁止额外字段；[array](https://json-schema.org/understanding-json-schema/reference/array)
支持 `items`、长度和 uniqueness。typed schema 应负责节点类型和局部约束。

[W3C XML Schema：keys and keyrefs](https://www.w3.org/TR/xmlschema-0/#specifyingKeys)
给出跨结构 referential integrity 的标准先例：key 唯一，keyref 的值必须在目标 key 集合存在。
JSON/YAML 的局部 schema 不能替代 repo-wiki 的 citation/source/diagram join pass。

[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)
严格定义 Markdown block、link reference definition 和 code fence 的解析。repo-wiki 应基于一个明确的
Markdown parser/AST 做引用提取，不能让 duplicate definition 被字典覆盖或让 fence 内容误算正文引用。

[Mermaid：syntax validation without rendering](https://mermaid.js.org/config/usage.html#syntax-validation-without-rendering)
提供 `mermaid.parse(text)` 验证 graph definition syntax；成功只返回 diagram type，不证明节点、消息或
状态转换有源码证据。

[Mermaid accessibility](https://mermaid.js.org/config/accessibility.html)
定义 `accTitle` 与 `accDescr`，并说明它们会成为 SVG title/description 和 ARIA 关联。

### 对 repo-wiki 的设计推论

#### 5.1 拆分 writer schema 与 Candidate schema

writer-owned draft frontmatter 应使用独立、严格模型，而不是复用允许 kernel/reviewer 字段的宽模型：

```yaml
coverage: full
sources:
  - id: valuation-entry
    resource: Accounting/src/.../ValuationService.java#L20-L61
diagram_evidence:
  - id: valuation-pipeline
    sources: [valuation-entry]
```

约束：

- `coverage` required，且只能是 literal `full | partial`；
- `sources` required，是 object array，不接受 path string array；
- source `id` 和 `resource` required，unknown fields forbidden；
- source ID 满足稳定 ASCII slug pattern，并在页内唯一；
- `diagram_evidence` 的 diagram ID 唯一，每个 source ID 必须 join 到 `sources`；
- kernel enrich 后再用完整 Candidate schema 验证 `id/type/title/path/language/diagrams/...`。

契约必须同时给失败示例和预期 error code：

```yaml
# invalid: folded scalar is still a string, but not an allowed enum value
coverage: >
  Covers most accounting paths.

# invalid: sources items must be objects
sources:
  - Accounting/src/.../ValuationService.java#L20-L61
```

反例帮助 writer 一次写对，但不是 validator 的替代品。

#### 5.2 Citation join

按以下顺序验证，避免把一个根错误扩散成几十个后续错误：

1. 解析 Markdown，保留每个 footnote ref/definition 的 occurrence，不静默覆盖 duplicate definition；
2. `source.id` 全部 required、格式合法、唯一；
3. `set(source ids) == set(footnote refs) == set(footnote definitions)`；
4. 每个 source 至少被引用一次，禁止未使用的 frontmatter source；
5. 每个 locator 解析到 registered Source/catalog 和 frozen revision；
6. line range 存在且落在继承 scope；
7. cross-source page 覆盖所有 participant Sources。

syntax/schema error 应先阻断 join；不要在 `sources` 还是字符串数组时继续发出几十个 locator error。

#### 5.3 Diagram evidence

图必须在 evidence capture 和 scope closure 完成后才允许进入 Composition。每张图分两套 gate：

| Gate | 能证明什么 | 不能证明什么 |
|---|---|---|
| Mermaid parse | fence 是被 pinned Mermaid version 接受的语法，diagram kind 可识别 | 节点/边/message 是否真实 |
| OKF evidence closure | diagram ID、caption、source IDs、participant Sources 和 locators 完整可解析 | 证据是否真正支持每一条关系 |
| Semantic review | 关键 node/edge/message/transition 与 evidence 一致，未漏失败/反馈路径 | 确定性 schema 正确性 |

cross-source sequence diagram 至少引用 producer、contract（若独立）和 consumer 的证据；含反馈箭头时还要
引用 feedback evidence。只有一个“图后有任意 citation”的检查不够。`accTitle`、`accDescr` 和图后可独立
理解的 evidence-backed conclusion 继续必需。

最终 syntax gate 应调用固定版本的官方 `mermaid.parse()`，而不是用正则重写 Mermaid grammar。可保留
轻量 Python structure check 作为早期反馈，但不能把它宣称为完整语法验证；运行时不得临时联网下载 parser。

## 6. Gate 所有权与失败时机

| Gate | 责任阶段 | 必须阻断的问题 |
|---|---|---|
| Plan schema | plan | scope/source/path/seed 结构错误 |
| Participant closure | plan | cross-source 缺 producer/consumer/contract/feedback evidence |
| Bidirectional routing | plan review | 只有 split probe、重叠 unit、伪 umbrella unit |
| Composition binding | composition | unit 未恰好绑定一次、page type/profile 不匹配 |
| IA routing | composition review | 机械 1:1、应 merge/split/move、平铺 capability path |
| Draft completeness | write | Composition 中任何 draft 缺失 |
| Draft frontmatter schema | write | coverage 长句、sources 字符串、unknown field、非法 ID |
| Citation/locator closure | write | join、revision、range、scope、cross-source coverage 失败 |
| Diagram syntax/evidence | write/review | 语法、ID、participant evidence、caption evidence 失败 |
| Navigation closure | publish | root/section index、orphan、broken link、未发布 leaf |

推荐 validator 短路顺序：

```text
YAML parse
  -> typed schema
  -> Plan participant/scope closure
  -> Composition unit/path/profile binding
  -> draft set completeness
  -> source-id/citation joins
  -> locator revision/range/scope
  -> Mermaid syntax
  -> diagram evidence closure
  -> index/navigation reachability
```

这样错误会回到最早负责的 Artifact：cross-source scope 缺失重开 Plan，错误 page grouping/path/profile 重开
Composition，writer 格式和 claim evidence 只重开当前 page。不要让 page writer 修它无权扩大的 scope。

## 7. 测试矩阵与完成定义

这是 contract 变更，按本仓库规则必须同步 models、validator、references、templates、tests、CLI e2e 和
live grade。至少保留以下 deterministic negative fixtures：

| Fixture | 最早预期错误 |
|---|---|
| plan units 机械一对一，未记录 merge probe | routing-probe-missing |
| 相邻薄页不独立但 reviewer 仍 approved | composition-review-invalid |
| 多页 Composition 全是裸文件名 | capability-path-missing |
| 非叶目录无派生 index | navigation-index-missing |
| published page 不可从 root index 到达 | navigation-orphan |
| integration unit 只有 producer scope | participant-closure-invalid |
| evidence locator 超出 participant scope | evidence-outside-scope |
| `coverage: >` 长说明 | frontmatter schema enum error |
| `sources: [path]` | frontmatter schema item-type error |
| duplicate source/footnote definition | source-id-invalid / citation-join-invalid |
| diagram 在 participant evidence 前被计划 | diagram-evidence-plan-invalid |
| Mermaid structure 看似合理但 parser 拒绝 | mermaid-syntax-invalid |
| diagram 只引用 producer、不引用 consumer | diagram-evidence-missing |
| Composition 21 页只生成 16 draft | draft-missing |
| progress 手写 unit 数与 Plan 不同 | 不再存在：数字由状态派生 |

Semantic live eval 不看 page count 或平均行数，而用真实维护问题比较：

- 一个问题是否一次路由到正确页；
- 是否需要跨多少页重建一条 causal chain；
- 回答中正确 locator 的比例；
- 是否遗漏 producer/consumer/feedback；
- 找到算法、公式、失败语义所需时间和 token；
- 同一 shared contract 被重复解释的次数。

完成标准不是“80 errors 清零”，而是错误机制前移：错误 scope 无法进入 Composition，机械 1:1 无法通过
Composition review，错误 frontmatter 无法进入 locator validation，证据不闭合的 diagram 无法进入 publish，
每个最终页面都能从根 index 渐进到达。

## 8. 不采用的替代方案

- 不设 merge 数量或目标 page 数；这会把 split-only 偏差改成 merge-only 偏差。
- 不用“每份 evidence 文件只能属于一个 Source”代替 claim-level Source/locator closure。
- 不让 writer 自行扩 scope；这会绕过 Plan ownership 和 frozen evidence boundary。
- 不让 `coverage: partial` 吞掉 planner-controlled omission。
- 不为 rule/orchestration/calculation 各造完整新 page type；`Domain profile` 足够表达模板差异。
- 不手写 index 或手写 progress count；都能从 Composition/Run state 确定性派生。
- 不用正则宣称完整解析 Markdown 或 Mermaid；使用标准 parser，另做 repo-wiki semantic joins。
- 不因这次 greenfield contract 变更增加旧 Run migration 或双 schema 分支。
